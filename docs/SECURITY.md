# 安全与隐私说明

## 1. 安全目标

- 源目录只读，任何情况下不修改、移动或删除游戏截图。
- 输出只写入用户指定、且位于源目录之外的目录。
- 不覆盖已有文件，不产生半成品。
- 不在界面、日志、失败清单、错误信息或 Git 中暴露密钥、令牌和完整用户目录。
- 更新包必须验签，更新失败不影响当前版本。

## 2. 威胁模型

| 威胁 | 缓解 |
|---|---|
| 误把输出写进源目录，导致重复扫描/覆盖 | 输入输出规范化、相等/嵌套/别名检查；拒绝 TapTap 根目录 |
| 通过 junction/symlink 逃逸 | 扫描和输出拒绝重解析点；以最近存在祖先规范化后校验 |
| 重名覆盖已有文件 | 默认跳过；自动重命名使用原子不覆盖语义 |
| 写入中断留下损坏文件 | 同目录临时文件 + 刷盘 + 原子改名；失败/取消清理 |
| 单个坏文件拖垮整批 | 单文件错误隔离，继续处理并记录原因 |
| 日志泄露目录/密钥 | 统一脱敏、只记录相对路径/原因码；发布前 secret scan |
| 恶意/损坏更新包 | Tauri Updater 公钥验签；HTTPS 端点；失败不安装 |
| 依赖供应链 | 官方 Actions、锁文件、Dependabot、最小 `GITHUB_TOKEN` 权限 |
| 本地用户读取配置 | 配置是用户数据，不含密钥；按操作系统用户权限保护 |

不防护：

- 已经控制本机并拥有当前用户权限的攻击者；
- 内存抓取、调试器、二进制补丁；
- 游戏客户端自身的其他安全问题。

## 3. 游戏 AES 材料

游戏使用固定 AES-256-CBC 密钥/IV。该材料会随发布二进制分发，**不是长期秘密**，也不能作为 DRM 或访问控制。

本项目的处理原则：

- 只在构建期通过 `HEARTOPIA_CRYPTO_MATERIAL_B64` 注入 48 字节（32 key + 16 IV）；
- `build.rs` 生成 `OUT_DIR` 数组，不写入源码、配置文件或仓库；
- 发布构建 `HEARTOPIA_RELEASE=1` 时缺失/长度错误直接失败；
- 不显示、不记录、不通过 IPC 返回；
- 公开仓库的合成测试只使用测试向量，不使用真实材料；
- 本地开发材料用当前用户 DPAPI 保存，仅临时注入构建进程。

即使遵循以上规则，有能力的本地逆向者仍可从二进制提取材料。安全边界应表述为“减少泄露面”，而不是“密钥不可获取”。

## 4. 路径与文件安全

- 所有来自前端的路径只作为“待校验输入”，不能直接拼接文件操作。
- 解密使用服务端扫描快照中的 ID 到真实路径映射，忽略前端提交的路径。
- 输出目录在任务开始时锁定；任务中不跟随新出现的链接。
- 目标文件存在时默认跳过；自动重命名必须原子地占用新名称。
- 受保护目录为盘符根下的 `TapTap` 目录（当前游戏安装与 HeartopiaDev 所在）；写入请求一律拒绝。输出还不得位于输入目录内部。
- 长路径、中文路径、Unicode 规范化差异和大小写不敏感文件系统需要测试覆盖。

## 5. 日志与界面隐私

- 界面只显示目录 basename、相对路径和最近目录别名。
- 手动路径输入使用密码遮罩，不进入 React 状态之外的持久化。
- 日志记录：时间、级别、相对路径/文件名、原因码、计数；不记录完整目录。
- 失败 CSV 只含相对路径与原因码。
- 错误消息映射为稳定中文文案；底层路径/密钥不拼接到 UI。
- 发布前运行 `node scripts/scan-secrets.mjs`，检查受跟踪和未忽略文件。

## 6. 更新安全

- 更新端点固定为 `https://github.com/Airisua/heartopia-photo-tool/releases/latest/download/latest.json`。
- 应用内置更新公钥；`latest.json` 中的 `signature` 必须是 `.sig` 内容。
- 启用 `requireSignedVersion`，要求 `.sig` trusted comment 含与公告版本一致的 `version:`；否则拒绝更新。只验签安装包字节而不绑定版本时，攻击者可把旧包配上更高版本号。
- 使用 NSIS 用户态安装（`currentUser`），避免更新时要求管理员权限。
- 禁止降级（`allowDowngrades=false`），防止旧漏洞版本被重新安装。
- 下载/校验/安装失败只更新 UI 状态；不删除当前版本，不清空配置。
- 私钥仅存于 GitHub Actions secret；丢失私钥将导致无法向已安装用户推送新版本。

## 7. 构建与供应链

- CI 使用 `npm ci` 和提交的 `Cargo.lock`/`package-lock.json`。
- GitHub Actions 权限最小化：CI `contents: read`，Release `contents: write`。
- 不在 `pull_request_target` 中执行不可信代码；不在日志打印 secret。
- Release 构建校验材料、配置和产物签名；构建后再次拉取线上 manifest 验证。
- 建议对第三方 Action 固定到受审计的 commit SHA；至少使用官方 Action 的主版本并定期审查。
- 发布前运行 `cargo audit`/`npm audit`（如可用），记录已知例外。

## 8. 漏洞报告

请不要在公开 issue 中提交密钥、真实用户路径或可利用细节。通过仓库维护者提供的私密渠道报告，并附：

- 受影响版本/提交；
- 复现步骤；
- 影响（读写越界、覆盖、信息泄露、更新绕过等）；
- 建议修复。

## 9. 已知限制

- 固定对称密钥可从二进制提取。
- 未购买代码签名证书时，SmartScreen 可能提示未知发布者。
- 极端异常（磁盘故障、强制断电、文件系统损坏）无法保证临时文件一定被清理；正常错误/取消路径会清理。
- 干净机安装、不同规模图片库的性能、真实更新链路必须按 `ACCEPTANCE.md` 实测，单元测试不能替代。
